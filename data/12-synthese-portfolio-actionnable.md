# Synthese actionnable - Portfolio BUT2

## Perimetre et filtrage

Cette synthese regroupe les attentes issues des notes PPP/portfolio, de la note d'intention portfolio, des notes de stage, des transcriptions de communication et des supports officiels de stage. Les informations personnelles, noms, exemples trop individuels, coordonnees, messages prives et details propres a un stage precis ont ete retires.

## Role du portfolio

Le portfolio attendu est un e-portfolio avec une dimension de portefeuille de competences. Il sert a la fois :

- a se presenter de facon professionnelle ;
- a montrer des realisations ;
- a prouver des competences ;
- a faire le lien entre la formation, les SAE, les projets, le stage et le monde professionnel ;
- a soutenir le bilan de stage pendant l'oral.

Le portfolio n'est pas seulement une vitrine graphique. Il doit demontrer une progression et une capacite d'auto-evaluation.

## Publics vises

Le portfolio doit fonctionner pour plusieurs lecteurs :

- enseignants evaluateurs ;
- tuteur professionnel ou jury de stage ;
- recruteur, entreprise, maitre d'apprentissage ou responsable d'alternance ;
- personne externe qui ne connait pas le referentiel BUT.

La solution la plus robuste consiste a avoir une base commune lisible professionnellement, puis une couche universitaire qui rend visibles les competences, apprentissages critiques, preuves et auto-evaluations.

## Trois fonctions a couvrir

### 1. Se presenter

La partie "a propos" doit rester professionnelle.

A inclure :

- profil court ;
- formation ;
- domaines d'interet professionnels ;
- type de missions recherchees ;
- technologies principales ;
- lien CV, Git, LinkedIn ou contact si partageable ;
- positionnement clair : developpement, web, mobile, data, logiciel, etc.

A eviter :

- details trop personnels ;
- ton trop amateur ;
- informations privees ;
- presentation vague du type "passionne par l'informatique" sans preuve.

### 2. Presenter les realisations

Le portfolio doit montrer des projets concrets :

- SAE S1/S2, plus synthetiques ;
- SAE S3/S4, plus detaillees ;
- missions de stage ;
- projets personnels pertinents ;
- experiences collectives si elles prouvent une competence.

Les notes insistent sur le fait que le portfolio ne se limite pas aux projets IUT. Les projets hors IUT peuvent etre integres s'ils renforcent la demonstration.

### 3. Demontrer les competences

Les notes de cours renvoient aussi au tableau du referentiel BUT Informatique pour identifier les competences et apprentissages critiques a relier aux SAE, projets et missions de stage. Cette reference est mentionnee en cours comme le document national du BUT Informatique, autour de la page 16 : elle sert d'appui, pas de texte a recopier integralement.

Le point central est l'articulation entre projets et competences. Il ne faut pas faire deux listes separees : une liste de projets d'un cote et une liste de competences de l'autre.

Chaque projet doit montrer :

- ce qui a ete fait ;
- le role exact de l'etudiant ;
- les traces disponibles ;
- les competences mobilisees ;
- pourquoi ce projet prouve ces competences ;
- ce qui a ete appris ;
- le niveau atteint et les axes de progression.

## Architecture conseillee

Une structure simple et defendable :

1. Accueil ;
2. Profil ;
3. Realisations ;
4. Stage ;
5. Competences ;
6. CV / contact.

La page "Realisations" peut contenir les projets IUT, personnels et collectifs. La page "Stage" doit etre ajoutee ou completee en fin de stage, avec une organisation par missions plutot que par "projet" si cela correspond mieux.

La page "Competences" ne doit pas etre une simple liste. Elle doit renvoyer vers les projets et missions qui les prouvent.

## Mode professionnel et mode universitaire

Le portfolio peut etre pense avec deux niveaux de lecture.

Mode professionnel :

- lecture directe ;
- vocabulaire comprehensible par une entreprise ;
- realisations, role, resultats, technologies ;
- preuves visibles ;
- peu de jargon universitaire.

Mode universitaire :

- competences BUT ;
- apprentissages critiques reformules ;
- justification des preuves ;
- auto-evaluation ;
- progression ;
- lien avec les attendus de l'IUT.

Il n'est pas necessaire de creer deux sites. Une meme page peut avoir une lecture professionnelle principale et des encarts universitaires plus explicites.

## Fiche type d'un projet

Pour chaque projet ou SAE, utiliser une structure homogene.

### Informations de base

- titre du projet ;
- periode ;
- cadre : SAE, cours, projet personnel, stage, equipe ;
- objectif en une phrase ;
- technologies principales ;
- role exact.

### Contexte et objectif

Expliquer le besoin :

- pourquoi le projet existe ;
- qui est l'utilisateur ou le destinataire ;
- quelles contraintes existaient ;
- ce qui etait attendu.

### Travail realise

Decrire concretement :

- responsabilites ;
- fonctionnalites ou livrables ;
- choix techniques ;
- methodes de travail ;
- contribution individuelle dans le cas d'un groupe.

### Traces et preuves

Ajouter ce qui peut etre partage :

- capture ;
- lien ;
- depot ;
- extrait de documentation ;
- schema ;
- maquette ;
- video courte ;
- resultat visible ;
- retour ou validation reformulee.

Une preuve doit etre comprehensible. Une capture sans explication ne suffit pas.

### Competences mobilisees

Relier le projet a quelques competences, sans surcharge.

Pour chaque competence :

- nom comprehensible ;
- lien avec une action concrete ;
- preuve associee ;
- niveau atteint ;
- point a ameliorer.

### Auto-evaluation

Courte, concrete, utile.

Questions :

- qu'est-ce qui a ete reussi ?
- qu'est-ce qui a ete difficile ?
- qu'est-ce qui a ete appris ?
- qu'est-ce qui serait refait autrement ?
- quel niveau de maitrise maintenant ?

## Fiche type d'une mission de stage

Le stage doit etre integre au portfolio en utilisant le terme "mission" quand c'est plus juste que "projet".

Structure conseillee :

- intitule de la mission ;
- contexte professionnel ;
- objectif ;
- environnement technique ;
- role dans l'equipe ;
- demarche de travail ;
- resultat ou livrable ;
- preuve anonymisee ;
- competences techniques ;
- competences transversales ;
- recul personnel.

Exemples de competences transversales a prouver :

- autonomie ;
- integration dans une equipe ;
- communication avec un tuteur ;
- organisation ;
- respect des echeances ;
- capacite d'apprentissage ;
- adaptation ;
- initiative ;
- resolution de probleme.

Ces axes recoupent la grille d'evaluation entreprise et peuvent donc renforcer le bilan de stage.

## Bilan de competences du stage

Les notes de cours indiquent que le portfolio sert aussi au bilan des acquis de stage. Ce bilan doit etre construit en parallele du rapport.

Deux plans possibles :

- par competences BUT mobilisees pendant le stage ;
- par types de missions, avec les competences croisees dans chaque mission.

Pour chaque axe de bilan, rediger :

- situation de depart ;
- mission ou probleme rencontre ;
- action realisee ;
- competence mobilisee ;
- preuve ;
- progression ;
- limite ou suite.

Le bilan doit montrer de la reflexion. Il faut eviter les phrases generiques comme "j'ai progresse en autonomie" sans expliquer sur quelle mission, avec quel obstacle, quelle decision et quel resultat.

## Utilisation pendant la soutenance

Pendant la soutenance de stage, le portfolio doit servir de support au bilan de stage.

La consigne reconstruite a partir des notes :

- ne pas presenter tout le portfolio ;
- ne montrer que la partie utile au bilan du stage ;
- faire une navigation commentee ;
- utiliser le portfolio plutot qu'une simple diapositive pour le bilan ;
- revenir rapidement au diaporama ensuite si necessaire ;
- justifier en introduction les choix de construction du site en quelques phrases.

Ce qu'il faut preparer :

- la page stage ouverte ;
- les ancres ou sections utiles ;
- une navigation courte ;
- une phrase de transition depuis le diaporama ;
- une capture de secours en cas de probleme de connexion.

## Choix de l'outil

Le choix de l'outil est libre, mais doit etre justifiable.

Criteres a expliquer :

- facilite de mise a jour ;
- qualite visuelle ;
- temps disponible ;
- publication en ligne ;
- maintenance ;
- possibilite d'ajouter des projets et missions ;
- accessibilite ;
- adaptation a une lecture professionnelle et universitaire.

L'important n'est pas de prouver que l'outil est le plus technique. L'important est de montrer que le choix sert l'objectif : produire un portfolio lisible, maintenable et utile.

## Design et lisibilite

Le portfolio doit etre professionnel, sobre et clair.

A privilegier :

- navigation simple ;
- titres explicites ;
- projets comparables dans leur structure ;
- preuves visibles ;
- textes courts mais precis ;
- distinction claire entre contexte, role, preuve et competence ;
- responsive correct ;
- coherence graphique.

A eviter :

- effet vitrine trop personnel ;
- surcharge d'animations ;
- jargon non explique ;
- blocs de texte longs ;
- projets sans role individuel ;
- competences listees sans preuve ;
- liens morts ;
- captures illisibles ;
- informations confidentielles.

## Gestion des preuves

Les notes personnelles montrent l'importance de demander et collecter les traces tot : photos, videos, captures, documents, preuves de presentation ou de realisation.

Methode :

- lister les projets et missions ;
- pour chacun, lister les preuves possibles ;
- verifier si elles sont partageables ;
- demander l'autorisation si besoin ;
- anonymiser ou recadrer ;
- stocker avec un nom clair ;
- associer chaque preuve a une competence.

Une preuve doit toujours repondre a une question : "Qu'est-ce que cela montre que je sais faire ?"

## Confidentialite et informations personnelles

Avant publication ou partage :

- retirer les noms non necessaires ;
- retirer les coordonnees ;
- retirer les donnees internes ;
- retirer les captures sensibles ;
- retirer les conversations privees ;
- verifier les droits sur photos et videos ;
- ne pas publier de code proprietaire sans autorisation ;
- ne pas exposer de secrets techniques.

Quand une preuve est sensible, utiliser :

- un schema simplifie ;
- une capture floutee ;
- un exemple fictif ;
- une description fonctionnelle ;
- une photo generique autorisee ;
- une reformulation.

## Checklist de construction

Fondation :

- definir les publics cibles ;
- choisir l'outil ;
- construire l'arborescence ;
- creer une page type projet ;
- creer une page type mission de stage.

Contenu :

- lister SAE S1/S2/S3/S4 ;
- lister projets personnels pertinents ;
- ajouter les missions de stage ;
- choisir les projets les plus representatifs ;
- rediger role, contexte, actions, resultats ;
- ajouter les preuves.

Competences :

- relier chaque projet a des competences ;
- eviter les competences sans preuve ;
- reformuler pour rester comprehensible ;
- ajouter une auto-evaluation courte ;
- indiquer les axes de progression.

Avant evaluation :

- verifier que le portfolio est en ligne ;
- tester tous les liens ;
- relire l'orthographe ;
- verifier la lisibilite mobile et desktop ;
- supprimer les informations personnelles ;
- preparer la navigation pour la soutenance ;
- preparer une phrase pour justifier les choix de structure et d'outil.

## Critere de qualite final

Un bon portfolio permet a un lecteur de comprendre rapidement :

- qui est l'etudiant professionnellement ;
- ce qu'il a realise ;
- quel role il a eu ;
- quelles preuves existent ;
- quelles competences sont demontrees ;
- comment il a progresse ;
- ce qu'il peut apporter dans un contexte professionnel.
